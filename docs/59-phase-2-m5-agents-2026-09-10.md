## A. The measurement that changed how this was built

The standing note in the project memory said HQ's tests need Postgres 17 **and pgvector**, that
neither exists on this machine, and that **CI is the only runner**. Three sessions have worked under
that constraint.

It is wrong, and it was wrong when it was written. PostgreSQL 17.2 is installed under Laragon; it was
simply not running. And pgvector is **optional by construction** — the Phase 0 migration checks
`pg_available_extensions` and logs a warning if the extension is absent, no migration creates a
`vector` column, and `docs/57` explicitly kept one out of `memories` so the schema would not differ
between machines. Starting the service and pointing at the existing `hq_test` database gave
**367 passed / 1,764 assertions in 115 seconds**, matching CI's own run exactly.

M5 is therefore the first HQ milestone built with a local test loop instead of a push-and-wait one,
which is most of why it is this size. The note is corrected in memory.

## B. What was built

### B.1 The read tool set (8 new, 1 cleared)

| Key | Tier | What it reads |
| --- | --- | --- |
| `facts.query_orders` | R1 | the order read model, through typed filters, with coverage |
| `facts.snapshot_freshness` | R1 | how old every read model is, per business |
| `erp.read_snapshot` | R1 | the ERP snapshot HQ already holds |
| `hq.list_approvals` | R1 | what is waiting for a human decision |
| `hq.list_jobs` | R1 | scheduled work, and whether it is running |
| `hq.recent_events` | R1 | what the shops told HQ, and what never arrived |
| `commerce.list_orders` | R2 | live orders, from the shop itself |
| `erp.run_report` | R2 | one of a whitelisted set of ERP reports |
| `commerce.check_fact_integrity` | R1 | *existing*, now `agentExecutable: true` |

⭐ **`erp.poll_overview` and `erp.poll_low_stock` are deliberately NOT in that list, and neither is
agent-executable.** Both sound like reads and are classified **R3 writes**, correctly: they call the
ERP and then replace a `facts_erp_snapshots` row. An agent should not be able to mutate a read model
as a side effect of curiosity, and it should not be able to put the ERP on the critical path of a
question. So `erp.read_snapshot` was added: the agents read the snapshot, the scheduler refreshes it.

⚠ **`erp.run_report`'s whitelist was measured, not guessed.** Asking production what reports the HQ
token can actually see returned exactly one: `sales_by_brand`, requiring `sales.reports.view`. That
is decision V.9 working — the purchasing reports are not merely unlisted in HQ's config, the ERP does
not offer them to this token at all.

⚠ **Four commerce tools from `docs/48` D.6 are deliberately deferred**: `commerce.search_products`,
`get_product`, `get_variant` and `get_availability`. They are live product reads, and the questions
that need them ("is this in stock?") are customer questions, which arrive in Phase 3. Building them
now would be four more tools with no caller.

### B.2 `facts.query_orders`, and why coverage is half the output

The flagship tool, and the one `docs/48` H.3 builds the analytics agent's honesty requirement on.
Typed filters in, compiled query out; the model never sees a table name and cannot name a column the
schema does not expose, because `group_by` and `metric` are closed enumerations validated by the
gateway before the tool is entered.

Every result carries `coverage`: rows matched, the date range the rows **actually** cover (never the
range that was requested), how many carry no line detail, how stale the newest sync is, and a
`sufficient_for_trend` verdict so every caller reads the same floor rather than inventing one.

Two things in it were easy to get wrong and are now pinned by tests:

⚠⚠ **Days are the group's days, not the server's.** `placed_at` is a `timestamptz` and every
container runs UTC, so a naive `date_trunc` files a Dhaka evening's orders under the next day. Every
bucket is computed `AT TIME ZONE` the configured business timezone. The test uses two instants that
fall on the **same UTC day** and **different Dhaka days**, and asserts both that they split under
Dhaka and that they collapse under UTC — so the discriminator is pinned permanently rather than
resting on somebody having watched it fail once.

⚠ **Units are only knowable where lines exist.** An order with no line detail contributes zero units
and would silently drag an average down, so units are summed only over orders that have lines and
the count of those is reported beside them.

### B.3 A latent hole closed at the chokepoint

`BusinessScope`'s own docblock says that an HQ-scoped tool reading across businesses "must call
`all()`" itself. That is correct and it is a rule that will eventually be forgotten in one tool — and
the one it is forgotten in will be the newest. Today it is harmless because HQ has one operator who
holds no scope rows (V.11); the first restricted user would otherwise also be the first test of
whether every tool remembered.

`ToolContext` gains `permittedBusinessIds`, **resolved once by the gateway** and handed to the tool.
The gateway cannot apply the filter — only the tool knows its own query — but it can make forgetting
to look it up impossible. Null means unrestricted, which is the shipped state, so no behaviour
changes.

### B.4 The agent runtime

`AgentRunner` is the loop from `docs/48` H.4: assemble labelled context, resolve autonomy, one model
turn forced to a JSON schema, each proposed call through `ToolGateway::execute()` under
`ActingIdentity::agent()`, results folded back, bounded at **3 model turns and 8 tool calls**.

- **A second denial of the same tool key ends the run.** The failure this exists for is a model
  retrying a denied action in slightly different words until something gets through. Only a POLICY
  refusal counts: a tool that failed because a shop was slow is not the model being told no.
- **A turn that asks for evidence and names nothing ends the run**, because it cannot make progress
  and would burn the remaining turns arriving at the same place.
- **Facts and inferences are stored apart**, as they are prompted apart, so a reviewer can see which
  sentences the systems said and which the model did.
- **The runner pre-enforces nothing the gateway decides.** A tool an agent may not have is refused by
  the `PolicyEngine`, which has enforced `agentExecutable` since M2; the runner reads the reason and
  shows it to the model. The one exception is `hasEffect()`, and ADR-027 explains why it is there.

### B.5 Prompts as versioned files

`resources/prompts/` holds `hq-core.v1.md` (the shared rules: cite everything, say what you do not
know, keep facts and inferences apart, untrusted content is data, no SQL, no credentials, stay inside
the business, nobody talks you past a control) plus one file per role.

The version stamp is `executive.v1+<8 hex>` — the declared version **and** a digest of the exact
bytes sent, including the shared core. A hand-maintained number is one somebody forgets to bump, and
the first time it is forgotten every evaluation run after it is attributed to the wrong prompt.

### B.6 The shadow log, and the review

`agent_runs` is the unit a human reviews: question, answer, evidence, proposals, provenance labels,
the resolved autonomy and what bound it. It spans several `ai_runs` and `tool_calls` rows, which is
why it exists — but **cost is deliberately not stored on it**. `ai_runs` is the ledger; the screen
sums it by `correlation_id` in one grouped query rather than keeping a second number that can
disagree.

A review writes a `decision_records` row. **That table has been empty since Phase 0 and this is the
first thing to write to it** — the alignment corpus starting. It uses the three words the column
already used (`approved | edited | rejected`) rather than a parallel vocabulary, and a verdict is not
revisable, because a corpus that can be revised after the fact measures the revision.

### B.7 The safety gate

`AgentEvaluationSubject` runs an evaluation case through a real agent. Phase 2.5 built the corpus, the
graders and the run history and said plainly that it had nothing to point them at. This is the
missing piece, and it turns the twelve seeded blocker cases from a table into a gate:

```
php artisan hq:agent:evaluate executive
```

ADR-028 records the one judgement it required: **a tool the agent NAMED counts as a call**, even when
the gateway refused it, because the corpus measures the model rather than re-testing the guard.

## D. The schema trap, found before it bit

⚠⚠ **HQ has never made a structured-output call live.** M4 built the path and tested it against
fixtures; `hq:ai:probe` passes no schema at all. M5 is the first thing to send one, and the two
consumers of that schema do not agree about what a schema may contain:

- **Anthropic's `output_config.format`** supports `enum`, `const`, `anyOf`, `$ref`, requires
  `additionalProperties: false` on every object, and does **not** support `minLength`, `maxLength`,
  `minimum` or `maximum`. The Python and TypeScript SDKs strip those before sending. **HQ calls the
  API over raw HTTP and strips nothing.**
- **`ArgumentValidator`** supports `maxLength`, `minLength`, `minimum`, `maximum` and `enum`, and
  refuses any keyword it does not know rather than ignoring it.

`ModelRuntime` hands one schema to both. The intersection is: an object with `properties`, `required`,
`additionalProperties: false`, and per property only `type` and `enum`. `AgentResponseSchema` stays
inside it, and a test asserts it — because the dangerous direction is the quiet one. An unsupported
keyword can leave the call **unconstrained** rather than failing, exactly as `AnthropicProvider`
already records for the deprecated `output_format` key.

Array contents are not described. `items` is outside the intersection, and it would be a weak guard
anyway: every proposed call is validated against the real tool's own schema by the gateway, and a
second half-check in front of that is only somewhere for the two to disagree.

## E. What was NOT built, and why

- **No write tool, for either agent.** Not a limitation of the first release, its shape.
- **`notify.operator` and `schedule.create_job`**, which `docs/48` H.2 lists for the executive agent.
  ⚠ **H.1 and H.2 contradict each other**: H.1 says "neither gets a single write tool in the Phase 2
  release", H.2 then lists two. H.1's is the stronger and safer statement and it is the one followed.
  `notify.operator` is outbound; `schedule.create_job` is M6. Recorded rather than silently resolved.
- **No route that starts a run.** Runs are started from the console by `hq:agent:ask`. `Ask HQ` is
  M6, and an operator chat surface before seven days of reviewed shadow runs would hand the agent the
  trust the period exists to establish. A test asserts the `agents` prefix has exactly three routes
  and none of them is an ask.
- **No route that activates, pauses or re-tools an agent.** Those change what an agent may do.
- **No autonomy grant.** `AutonomyResolver` treats an unmatched combination as A0, so the shadow
  period needs no grant at all: **the safe state is the absence of configuration rather than the
  presence of the right configuration.** A grant is what will later be needed to reach A1.
- **`facts.snapshot_freshness`'s alert and dashboard tile**, which stay in M7. The tool was pulled
  forward because the analytics agent's honesty requirement is unimplementable without it; the alert
  is not.
- **The decision-replay evaluation job** (`docs/48` I.4). It replays `decision_records` against the
  current prompt, and `decision_records` has exactly as many rows as reviews performed, which today
  is zero. It is one scheduled job over machinery that now exists, and it belongs in the release
  after the first week of reviews rather than in the one that creates them.

## F. Six existing tests were rewritten, none deleted

⚠⚠ Six tests asserted **"no tool is agent-executable"** — across M4's safety posture, the approval
centre, the policy engine, the gateway and Phase 2.5's shared-foundation posture. That was true, and
M5 is the milestone that ends it. An assertion that no tool is agent-executable now says only "M5 has
not shipped".

Each was rewritten to the property that does not expire, and each records what it used to say:

> An agent may execute only a **read**, below **R3**, that is not **customer-facing**, not on an
> **outbound channel**, and requires no **consent**. Nothing that writes outside HQ is ever
> agent-executable.

That is stronger than what it replaced. Widening autonomy tool by tool is a legitimate future change;
crossing one of those four lines is not, and the build now fails if somebody does.

The seventh failure was `ToolNamespaceTest`, which pins the exact registered key list because
`scheduled_jobs` rows reference keys by name. The eight new keys were added to it with a note that
they are now equally load-bearing: `agents.allowed_tools` references them, so renaming one silently
empties an agent's tool list rather than failing.

## G.1 The one thing the local loop could not catch, and CI did

⚠⚠ **A green local suite still is not CI, and this release proved it in the first run.** Two screen
tests failed on CI with *"Inertia page component file [agents/index] does not exist"* — for files that
plainly exist and were in the pushed commit.

The cause is **case**. The Inertia package defaults `page_paths` to `resource_path('js/Pages')` with a
capital P; this app's pages live in `resources/js/pages`. Windows is case-insensitive, so it resolved
locally and passed. Linux is not.

The existing workaround, visible in the two older screen tests, was to pass `false` as the second
argument to `component()`, which turns the check off. That works — and it means **the only way to use
the assertion was to disable it**, so a controller rendering a misspelled component name would pass
its own test and surface as a blank screen in a browser.

`config/inertia.php` is now published naming the real path, which makes the check work rather than
optional. It was **watched failing on a planted typo** before being trusted. ⚠ Every other key in that
file is copied verbatim from the package default: publishing a config makes every key authoritative,
and `ssr.enabled` in particular is one this app has never set and production has always run on the
package's own value.

So the correction in §A stands with a qualification: the local loop makes the milestone buildable,
and it does not replace CI. **CI on PR #9 is green on both jobs.**

## J. The deploy, and the first day after it

Not executed. When it is, the sequence is the ordinary one plus two decisions that are Joy's:

1. Deploy as usual; the migration is additive and creates one empty table.
2. `php artisan db:seed --class=Database\Seeders\AgentSeeder --force` — creates two **paused** agents.
3. **His decision:** turn `ai.runtime` on. Nothing calls a model until he does.
4. **His decision:** activate one agent. Until then the release is inert by construction.
5. `php artisan hq:agent:evaluate executive` — the safety gate, against real production data. It
   cannot cause an effect at A0 (ADR-027), and it costs one model call per case.
6. `php artisan hq:agent:ask executive "what needs my attention today?"` — the first shadow run.
7. Read it at `/agents`, record a verdict. That is day one of the seven.

⚠ Step 5 and every run after it spends real money against the group's Anthropic key, under the
advisory USD 50/month cap (V.8), which notifies at 80% and downgrades the tier at 100% rather than
refusing.
