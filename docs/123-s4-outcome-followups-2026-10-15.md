## Plan, piece by piece (each piece a WIP commit)

1. **The S3 link (Stage 4, item 1/D4, D7).** A follow-up becomes one more S3 action type, exactly as docs/107 D7 anticipated ("one more action type, one column"): `outcome_attributions.follow_up_id`, typed, RESTRICT, the typed-action CHECK replaced to include it (additive migration). Only a `done` follow-up can be credited, and only to an outcome of its own business (the recorder's existing checks). The writing path stays the ruled one: `OutcomeRecorder`, reached by the human-only `outcomes.attribute` tool, method `operator_asserted`. `afterCompleted` records nothing automatically, because v1 admits no method that could link a person's contact to a later result (Q3: `rule_window` inactive; C7). The real `FollowUpOutcomeLink` binding reads the current (D17) credited outcomes for follow-ups and opportunities, restricted twice (viewer `BusinessScope` and the row's own business). An opportunity closed `converted` is shown as supported or not supported by the ledger (docs/113 F4), never replaced by it.
2. **Customer 360 follow-ups section (item 14).** A separate read-only reader, scoped by the customer's `business_id` AND the follow-up's `business_id`, shown only to a viewer holding `hq.followups.view`. Promises are the `promise`-origin follow-ups. No write control, no form, no button. One line in `Customer360Reader::read()` so the merge with the identity stream stays small.
3. **Overdue alert (item 16).** A new alert rule `followups.overdue` beside the existing sixteen. One condition per responsible person (the person who approved the follow-up, who is also its run's requester). The engine sends it to that person only, in HQ (an addressed in-app record and a sidebar badge), never on the shared channel and never to a customer. No outreach, no state change.
4. **Retention (item 13, item 7).** Refused and declined follow-ups and declined opportunities are pruned 365 days after the decision; done, cancelled and closed rows are kept (their applicable rule is "relationship history, kept"); open rows never. Keep-clauses win: a follow-up an attribution credits, and an opportunity a follow-up still points at, are kept. The WorkflowEngine rule (terminal and reconciled, 180 days) is the existing one and applies to follow-up runs unchanged; a test pins that a pruned run leaves its follow-up intact. One new DELETE site, pinned like the workflow one.
5. **Roles (item 11).** Deciding needs `hq.followups.decide`, checked in the service; proposing never confers it; brand_manager and support_agent hold view and propose only (pinned). A decider deciding on their own proposal is recorded visibly (audit flag and screen label).
6. **Vocabulary (item 12, item 10).** One versioned vocabulary class (`followups.vocabulary.v1`) naming every kind, origin, state and close reason; database CHECKs on every vocabulary column; a pin test so a change is a reviewed change. No `transactional` kind.
7. **RESTRICT (item 15).** A database test over `pg_constraint`: every foreign key on `follow_ups`, `opportunities` and the new attribution column is RESTRICT.
8. **Structural pin (item 17, item 8).** The pin that compared the definitions list to a class name is replaced by a test over the workflow DEFINITIONS themselves: every definition in the live catalogue and in `config/hq.php` declares only sleep and signal steps, no tool key, no tool arguments, and no `Step::tool` in its source; a negative control proves the checker catches a tool step. The person-decision signal is sent only by the follow-up service.
9. **Consent fail-closed (item 9).** Tests: missing or unresolved consent refuses; a refused row is final (recording consent later never revives it; a new proposal is needed); the follow-up code never records consent itself.

All outbound paths stay absent. No flag, no provider, no agent tool. Bangla for every new string.
